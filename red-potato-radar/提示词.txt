# 红薯雷达：Windows 桌面软件完整开发提示词

请直接为我开发并交付一套完整可运行、可打包、可分发的 Windows 桌面软件。不要只输出产品方案、界面示例、伪代码或零散片段；请创建完整项目文件，运行调试，修复错误，并在环境允许时打包出双击即可运行的 EXE。

**软件定位：** 监控用户主动添加的小红书公开商品，定时记录商品累计已售、价格、店铺等公开信息，通过相邻快照计算商品和店铺的小时销量、今日销量、昨日销量与历史趋势。所有业务数据保存在本机 SQLite 数据库中。

> **执行要求：** 请严格按照下面的规格一次性完成。

## 一、交付目标

**交付内容至少包括：**

1. 完整 Python 源码。
2. SQLite 数据库初始化与自动迁移代码。
3. Windows 桌面图形界面。
4. 定时采集与三级采集兜底逻辑。
5. 企业微信机器人通知。
6. 只读 MCP 数据服务。
7. `requirements.txt`。
8. `README.md`。
9. 一键打包脚本 `build.bat`。
10. PyInstaller `.spec` 文件。
11. 最终无控制台黑框的单文件 EXE。

代码必须是可维护的正式实现，不要把全部功能堆在一个巨大函数里。建议将界面、数据库、采集、统计、通知、MCP拆分成独立模块；如果为了便于分发选择少量文件，也必须通过类和函数清晰分层。

## 二、技术栈

- Python 3.11 或 3.12。
- GUI：Tkinter + ttk，禁止依赖需要单独安装运行环境的前端框架。
- 数据库：SQLite，开启 WAL 模式，所有表都要自动创建，旧数据库缺少字段时自动迁移。
- HTTP：标准库 `urllib.request`，可使用系统 `curl.exe` 作为补充请求方式。
- 浏览器兜底：Playwright。优先使用系统 Chrome，其次 Microsoft Edge，最后使用 Playwright Chromium。
- 图片：Pillow，用于商品主图缩放与展示。
- 打包：PyInstaller，`--onefile --windowed`，运行时不得出现命令行黑框。
- 时间口径：全部使用 `Asia/Shanghai`。
- 软件首次运行自动在 EXE 同目录生成 `monitor.db` 和必要的数据目录。
- 所有外部进程在 Windows 下都要使用 `CREATE_NO_WINDOW` 或等价配置，避免采集时反复闪现黑色命令窗口。

## 三、商品输入和解析

**“添加商品”必须同时支持以下四种输入：**

1. 小红书分享口令，例如包含标题、表情、短链和提取码的一整段文字。
2. `xhslink.com` 短链。
3. 完整商品链接，例如 `https://www.xiaohongshu.com/goods-detail/商品ID?...`。
4. 单独输入24位十六进制商品 ID。

还必须支持批量导入：文本框中一行一个，可混合放入口令、短链、完整链接和商品 ID。

**解析规则：**

- 优先用正则从整段文字中提取 `/goods-detail/` 后的24位 ID，或者直接提取独立的24位十六进制字符串。
- 短链需要跟随重定向，再从最终地址或返回页面中提取商品 ID。
- 商品 ID 统一转成小写。
- 批量导入时按 ID 去重，已经存在的商品跳过并计入“重复”。
- 单个添加时，先采集并展示商品名称、店铺、实际价格、累计已售，再弹窗让用户确认是否加入。
- 批量添加结束后显示：成功、待采集、下架、重复、超过销量上限、无效输入各有多少个。

## 四、商品详情接口和字段解析

**商品接口：**

```text
https://mall.xiaohongshu.com/api/store/jpd/edith/detail/h5/toc?version=0.0.5&item_id={商品ID}
```

从 `data.template_data[0]` 中解析：

- 商品标题：优先 `descriptionMain.name`，回退 `descriptionH5.name`。
- 店铺名称：`sellerH5.name`。
- 店铺 ID：`sellerH5.id`。
- 商品主图：`carouselH5.images[0].url`，以 `//` 开头时补 `https:`。
- 累计已售：`priceH5.itemAnalysisDataText`，支持“已售123”“1.2万”“1.2w”等格式。
- 店铺累计销量：`sellerH5.salesVolume`。
- 实际购买价格：优先 `priceH5.dealPrice.price`，其次 `bottomBarMainH5.dealPrice.price`，再次 `priceH5.highlightPrice`。不能用优惠前原价覆盖实际到手价。
- 粉丝数：`profitBarPopupH5.follow.fansNum` 或 `sellerH5.fansAmount`。
- 库存状态：`carouselH5.stockStatus`。
- 是否可配送：`bottomBarMainH5.deliveryInfo.ableToDelivery`。

只有当接口明确 `success=true`、`template_data` 完整存在时，空的已售字段才可以解释为真实 0。请求超时、状态码异常、返回体不完整、页面未加载、JSON解析失败、元素缺失或安全校验时，绝对不能用0代替，应判定本次采集失败，不保存假快照。

累计已售按高水位处理：统计时取历史可信累计值的最大值，防止偶发读取变小造成虚假负销量。若新读数小于历史高水位，本轮不应用这个较小值计算销量。

累计已售超过10000的商品不支持监控：添加时直接提示并跳过；存量商品一旦明确超过10000，移出监控，停止继续请求。

## 五、三级采集策略

每个商品必须严格按以下顺序独立执行，不允许先把全部商品都走完第一种方式再统一走第二种方式：

1. 轻量接口直采。
2. 当前商品直采失败后，立即使用静默浏览器采集。
3. 静默浏览器仍失败时，立即使用可见浏览器兜底。
4. 当前商品完成后，下一个商品重新从轻量接口直采开始。

### 静默浏览器要求

- 使用 Playwright 持久化 Context。
- `headless=True`，不显示窗口。
- `locale=zh-CN`，`timezone_id=Asia/Shanghai`。
- 设置合理 `viewport`。
- 整轮任务复用同一浏览器上下文，不要每个商品新开一个浏览器进程。
- 优先在浏览器中直接打开商品接口；接口无完整数据时再打开商品详情页，让页面建立正常会话后重新读取接口。

### 可见浏览器要求

- 只作为最后兜底。
- 每次进入可见兜底前创建新的临时 Profile，避免长期受限的旧环境一直失败。
- 打开该商品详情页，再读取商品接口。
- 当前商品成功或明确失败后关闭窗口，继续下一个商品。
- 默认逐个商品处理，不要一次打开多个页面。
- 临时 Profile 使用完后安全清理。

浏览器不可用时，要明确提示用户安装最新版 Chrome 或 Microsoft Edge，不能直接崩溃。

请求之间默认随机等待0.1～0.3秒，并允许在设置页修改为0.1～60秒。使用随机区间而不是固定值。

## 六、异常分类、重试和熔断

必须区分“临时失败”“风控”“明确下架”，不能混在一起。

1. HTTP 500、连接超时、连接重置、DNS临时错误、`Network.getResponseBody`、`Execution context was destroyed` 等属于临时错误。首轮先继续采集其他商品，在整轮结束后等待5～15秒，再统一重试一次。
2. HTTP 461 属于请求环境受限。单轮连续出现少量461时记录；达到阈值后立即停止继续请求，把未完成商品加入队列，冷却15分钟后自动续采，禁止高频循环重试。
3. 自动重试成功后应从失败列表移除，并照常生成本地数据和企业微信时报。
4. 一个商品失败不能卡死整轮任务，除非触发全局461熔断，否则必须继续下一个商品。
5. 所有错误都要捕获并写入运行日志，界面线程不能因为后台异常退出。

## 七、下架识别和下架列表

三种采集路径都必须识别下架：轻量接口、静默浏览器、可见浏览器。

**明确下架特征包括：**

- JSON 中购买按钮 type=unBuyableGoShop。
- 页面或接口文字包含“已下架，进店逛逛”“当前商品已下架”“商品不存在”“商品已失效”等明确状态。
- 页面包含“当前商品违规，无法展示”、item freeze 等违规状态。

不要仅凭网络错误、空白页面或超时判定下架。只有出现明确业务特征才能转入下架列表。

**确认下架后：**

- 设置商品 active=0。
- 记录 delisted_at 和 delisted_reason，原因区分“商品已下架”和“违规下架”。
- 清除普通失败状态。
- 保留该商品原有历史销量快照。
- 从竞品看板、店铺分析和以后所有采集任务中排除。
- 继续采集下一个商品，不能停在当前商品。

“下架列表”位于“失败列表”旁边，表格列为：商品名称、店铺、商品 ID、下架时间、下架状态。双击可查看下架前的单品历史数据。

## 八、定时任务和整点规则

- 默认采集周期60分钟。
- 用户在非整点点击“开始监控”后，不立即把该时刻当正式整点；例如09:35启动，第一次正式采集为10:00，下一次11:00。
- 支持修改周期，但必须按自然时间边界调度。
- 每轮采集使用该轮整点作为统计归属时间。
- 如果21:00轮次尚未完成，时间已经到22:00，必须停止21:00剩余任务，立即切换到22:00轮次；不得让旧任务无限积压。
- 同时只能运行一轮采集，使用线程锁避免“定时采集”和“立即采集”重叠。
- GUI必须保持响应，所有网络和数据库重任务放在后台线程，界面更新通过主线程调度。

## 十、销量统计口径

所有销量都由累计已售快照的差值计算，不能把累计已售直接当作当日销量。

- 今日销量：当前可信累计已售减去今日00:00的累计高水位。
- 昨日销量：今日00:00累计高水位减去昨日00:00累计高水位。
- 上小时销量：当前整点累计高水位减去上一个完整整点小时的基线。
- 某日销量：次日00:00累计高水位减去当日00:00累计高水位。
- 当日每小时销量：相邻整点累计高水位差值。
- 0点快照既是前一天结束值，也是新一天基线，不能重复计入两天。
- 若软件当天中途才开始监控，没有00:00快照，可以使用当天第一条真实成功快照作为起始基线，但界面要允许显示为不完整口径。
- 缺少足够基线时显示“—”，不要伪造0。
- 确认两个真实快照累计值相等时，销量增量才显示0。
- 模糊销售额：销量增量 × 当时实际价格，并明确标注“模糊试算，不代表真实成交额”。
- 所有统计函数都应处理跨日、0点、缺少快照、重复快照和累计值偶发回退。

## 十三、智能去重

竞品看板“自动拓品”旁放“智能去重”按钮。

**只有同时满足以下条件才视为重复：**

- 同一店铺。
- 商品标题标准化后完全相同。
- 累计已售相同。
- 上小时销量相同。
- 商品 ID 不同。
- 价格不同。

每组只保留价格最高的商品，其他候选在删除前弹窗预览并二次确认。任一关键字段为“—”时不参与去重，避免误删。

## 十四、自动拓品和同店商品发现

> **当前限制：** （已无法使用，小红书不再支持未登录状态电脑版查看店铺商品）

添加主商品成功后，根据 shop_id 打开对应店铺主页，解析店铺内其他商品。店铺卡片中可能同时有 itemId 与 skuId，详情接口优先使用 skuId。

**自动拓品按钮执行：**

1. 遍历当前监控商品对应的去重店铺。
2. 扫描店铺公开商品。
3. 排除已监控、已删除、已下架和本次重复的商品 ID。
4. 对新商品获取标题、店铺、销量、价格和封面。
5. 弹出选择窗口，列出勾选框、标题、店铺、销量、价格、商品 ID。
6. 支持单选、全选、取消全选和批量加入监控。
7. 添加单个商品时，如果店铺还有其他未监控商品，提示“店铺还发现了其他X个商品”，展示名称和价格，由用户决定是否一起添加。
8. 店铺扫描失败只能记录该店铺失败，不能导致整个自动拓品任务退出。

## 十五、失败列表

**按钮：全选、重试选中、忽略选中并保留监控、删除选中、刷新。**

- 所有操作支持单个和批量。
- 重试成功后自动移出失败列表并恢复正常。
- 重试后明确下架则移入下架列表。

- 双击失败商品也能查看已有历史数据。

设置页提供：Webhook输入框、启用复选框、发送测试通知按钮、设置通知店铺按钮、当前状态文字。

“设置通知店铺”点击后弹出店铺选择窗口，支持全选、取消全选、搜索和保存。只有勾选的店铺发送时报；没有勾选的店铺不通知。

每轮正式采集完成后发送店铺销量时报，按上小时销量从高到低排序。示例格式：

```text
📊 12点店铺销量时报
08月17日 12:00 - 12:59

🥇 XXXXXXXX的店
上小时销量：22 单
今日总销量：24 单

🥈 XXXXXXXX的店
上小时销量：16 单
今日总销量：20 单
```

前三名可使用奖牌符号，其他店铺使用序号。店铺名、上小时销量和今日销量要清楚分行，消息过长时自动拆分，不能超过企业微信机器人单条限制。

若有失败商品，再发送采集失败通知，包含时间、采集方式、失败数量、商品名称、商品 ID 和原因。明确下架商品不作为临时失败反复通知。

Webhook必须校验格式，发送失败写入日志但不能影响采集数据保存。

## 十九、只读 MCP 服务

提供独立 `mcp_server.py`，使用 stdio 通信，只读打开同目录 `monitor.db`。不得提供增删改工具。

**至少提供以下工具：**

- `list_shops`：店铺列表、监控商品数、今日销量、上小时销量。
- `list_products`：商品列表，可按店铺、关键词、状态筛选。
- `get_product_sales`：指定商品某日小时销量或近N天每日销量。
- `get_shop_sales`：指定店铺某日小时销量或近N天每日销量。
- `get_product_ranking`：按今日、昨日、上小时、累计已售、模糊销售额排名。
- `get_shop_ranking`：按店铺今日、昨日或上小时销量排名。
- `search_products`：按标题、店铺和商品 ID 搜索。
- `get_overview`：商品数、店铺数、今日销量、昨日销量、上小时销量、数据截止时间。

所有返回结果要包含口径和数据时间。MCP查询与桌面界面使用同一套统计函数，避免两个地方结果不一致。

**设置页生成的配置话术示例：**

> 请帮我配置一个本地 MCP 服务器，名称设为 `xhs-sales-monitor`。服务器使用 `stdio` 通信，命令路径是：[这里自动填入 `红薯雷达MCP.exe` 或 `mcp_server.py` 绝对路径]。配置完成后请连接并调用 `tools/list` 验证。这个 MCP 用于读取我本机红薯雷达中的小红书店铺、商品、销量、销售额和排名数据；只允许读取，不要修改数据库。

## 二十、运行日志

日志必须保存在 SQLite，重启不丢失。

日志字段：时间、级别、来源、商品、商品 ID、摘要、完整详情。

**界面要求：**

- 按“全部、成功、失败、信息”筛选。
- 刷新。
- 清空日志，二次确认。
- 导出 CSV。
- 双击查看完整异常详情并支持复制。
- 商品采集失败时展示真实异常，不要只写“失败”。
- 日志最多加载合理条数，避免界面卡顿。

## 二十一、本地数据占用和一键清理

右上角实时显示数据库占用大小和快照数量，例如：数据占用：19.1MB · 31,386条。

**提供“一键清理”：**

- 默认保留最近90天销量快照。
- 每个商品保留一条更早的基线，不能因为清理导致近期销量无法计算。
- 日志默认保留30天。
- 执行 `WAL checkpoint` 和 `VACUUM`。
- 清理前二次确认，清理后显示删除快照数、删除日志数、保留基线数和释放空间。
- 清理逻辑始终可用，与其他功能开关无关。

## 二十二、稳定性和安全要求

- 不在源码中写死个人 Cookie。
- 浏览器 Profile、Cookie文件和数据库只保存在本机。
- 日志不要输出 Cookie、Webhook完整值或其他敏感字符串。
- 所有后台线程异常都要转成用户可读提示。
- 关闭软件时尽量关闭 Playwright Context 和临时进程。
- 数据库写入使用事务，防止中途退出留下半条记录。
- 图片下载、商品请求、通知均设置超时。
- 任何失败不能让整个 GUI 崩溃。
- 对长标题、空店铺、无封面、零销量、价格缺失、跨日和夏令时无关的上海时区进行处理。
