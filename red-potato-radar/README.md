# 红薯雷达（Red Potato Radar）

> **仅供学习交流，严禁用于商业用途，请于 24 小时内删除。**
> 本工具只读取小红书**公开**商品页面上任何人都能看到的信息（商品名、店铺、价格、
> 累计已售等），用于本机销量趋势统计与研究。请遵守目标网站的服务条款与相关法律法规。

一个 Windows 桌面软件：监控你主动添加的小红书公开商品，按自然整点定时采集快照，
通过**相邻快照的累计已售差值**推算商品与店铺的小时销量、今日销量、昨日销量与历史趋势。
全部业务数据保存在本机 SQLite 数据库，同时提供一个**只读** MCP 服务供 AI 助手查询。

## 一、功能概览

| 能力 | 说明 |
| --- | --- |
| 商品输入 | 分享口令 / `xhslink.com` 短链 / 完整商品链接 / 单独 24 位商品 ID，可四类混排批量导入 |
| 定时采集 | 按**自然时间边界**调度（09:35 开始监控 → 首次 10:00，之后 11:00），周期可改 |
| 三级兜底 | 轻量接口直采 → 静默浏览器 → 可见浏览器，逐商品独立执行 |
| 异常区分 | 临时失败 / 风控(461) / 明确下架 三类严格区分，绝不混淆 |
| 销量统计 | 高水位累计已售差值：今日、昨日、上小时、某日、当日逐时、近 N 日 |
| 竞品看板 | 搜索、四列排序、多选批量采集、双击详情、右键菜单 |
| 店铺分析 | 以店铺为核心：逐时折线图、多日折线图、销量明细、店内商品表 |
| 智能去重 | 同店铺 + 标题标准化一致 + 累计已售一致 + 上小时一致 + ID 不同 + 价格不同 |
| 失败 / 下架列表 | 分列管理，支持重试、忽略、恢复、删除、批量操作 |
| 企业微信通知 | 每轮整点时报（前三名奖牌）+ 采集失败通知，超长自动拆分 |
| 运行日志 | 落库、筛选、导出 CSV、查看完整异常详情与复制 |
| 只读 MCP | 8 个读取工具，stdio 通信，数据库以 `mode=ro` 打开，物理上无法写入 |
| 一键清理 | 保留近 90 天快照 + 每商品 1 条基线，日志保留 30 天，WAL checkpoint + VACUUM |

## 二、环境要求

| 项目 | 要求 |
| --- | --- |
| 操作系统 | Windows 10 / 11（64 位） |
| Python | **3.11 或 3.12**（推荐 3.12；必须是带 tkinter 的标准发行版） |
| 浏览器 | Google Chrome 或 Microsoft Edge（用于浏览器兜底采集）；二者都没有时可安装 Playwright Chromium |

## 四、快速开始

### 方式 A：直接用打包好的 EXE

1. 把 `红薯雷达.exe` 和 `红薯雷达MCP.exe` 放在**同一个文件夹**（两者默认共用同一个 `monitor.db`）。
2. 双击 `红薯雷达.exe` 即可，首次运行会在同目录自动生成数据库与数据目录。
3. 本机需已安装 Chrome 或 Edge，浏览器兜底采集才能生效。

### 方式 B：从源码运行

```bat
cd red-potato-radar

:: 1) 创建虚拟环境（推荐，避免污染系统 Python）
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

:: 2) 安装 Playwright Chromium（作为 Chrome/Edge 之后的最后兜底，可选）
.venv\Scripts\python.exe -m playwright install chromium

:: 3) 启动
.venv\Scripts\python.exe app.py
```

### 首次使用建议流程

1. 打开「**添加商品**」，粘贴商品链接或分享口令，点「解析并添加」。
   单个添加会先采集并在弹窗里展示商品名、店铺、实际价格、累计已售，确认后再加入。
2. 回到「**竞品看板**」，点「**开始监控**」。
   若当前不是整点，第一次正式采集会发生在下一个自然整点（顶部会显示具体时间）。
3. 想立刻看效果，可点「**立即采集**」（会中断正在进行的轮次并重新开始）。
4. 在「**设置**」里按需配置企业微信通知与采集周期。

## 五、界面说明

窗口默认 1280×780，最小 1050×650。顶部固定显示：
**数据占用与快照条数**、**运行状态**、**下次采集时间**，以及可点击的 `by：冬青`。
标题区域始终显示免责声明。

### 1. 竞品看板

顶部左侧为标题与搜索框（实时匹配商品名称 / 店铺 / 商品 ID）；
右侧按钮**从右向左**依次为：添加商品、自动拓品、智能去重、立即采集、开始/停止监控。

表格列：商品名称、店铺、当前价格、今日销量、昨日销量、上小时销量、累计已售、最近采集、状态。

- 今日销量、昨日销量、上小时销量、累计已售 **四列点击表头可排序**，再次点击切换升降序，默认今日销量从高到低。
- **双击**商品打开单品数据弹窗；**右键**支持「查看详情 / 立即采集选中商品 / 删除商品」。
- 支持 `Ctrl` / `Shift` 多选并批量采集。删除商品需**二次确认**，删除后不再采集。
- 状态：待首次成功采集显示「待采集」，最近一次失败显示「异常」，成功显示「正常」。

### 2. 添加商品

支持四类输入混排，一行一个。可先点「解析预览」查看识别结果。批量添加结束后显示：
成功、待采集、下架、重复、超过销量上限、无效输入各多少个。

### 3. 失败列表

只放**临时采集失败与环境错误**，不放明确下架商品。
列：商品名称、店铺、商品 ID、最近失败时间、失败原因。
按钮：全选、重试选中、忽略选中并保留监控、删除选中、刷新。
- 重试成功 → 自动移出失败列表并恢复正常；
- 重试后明确下架 → 移入下架列表；
- 忽略 → 只清除当前提示，下一轮仍会继续采集。

### 4. 下架列表

列：商品名称、店铺、商品 ID、下架时间、下架状态（区分「商品已下架」与「违规下架」）。
双击可查看下架前的单品历史数据。支持「恢复监控」与「删除选中」。

### 5. 店铺分析

以**店铺**为核心。顶部店铺选择器 + 日期选择器，以及「查看该日逐时」「近 7 天」「近 10 天」。

- 选中某日 → 该店铺 **24 小时销量折线图**与明细；
- 近 7 天 / 近 10 天 → 对应自然日的**每日销量折线图**。
- 下方左右分栏：左侧**销量明细表**（时间、销量增量、模糊销售额），
  右侧**店铺内监控商品表**（商品名称、今日销量、当前价格、累计已售、商品 ID），默认按今日销量降序。
- 双击商品打开单品弹窗。

### 6. 设置

三组纵向卡片，内容较多时可滚动：

1. **监控设置**：采集周期（默认 60 分钟）、商品间隔最小/最大秒数（默认 0.1 ~ 0.3）、
   保存设置、打开浏览器处理验证、当前商品数量与预估单轮等待时间。
2. **企业微信机器人通知**：Webhook 输入框、启用复选框、发送测试通知、设置通知店铺、当前状态。
3. **AI / MCP 数据读取**：可复制的 MCP 配置说明 + 「复制 MCP 配置说明」按钮，并声明 MCP 只读。

### 7. 运行日志

按「全部 / 成功 / 失败 / 信息」筛选，支持刷新、清空日志（二次确认）、导出 CSV。
**双击**查看完整异常详情并支持一键复制。界面单次最多加载 1000 条，避免卡顿。

## 六、采集策略与异常处理

### 三级兜底（逐商品独立执行）

对**每一个商品**，严格按顺序执行，当前商品完成后下一个商品重新从第一级开始：

1. **轻量接口直采** —— `urllib.request`（必要时补充系统 `curl.exe`）
2. **静默浏览器** —— Playwright 持久化 Context，`headless=True`，
   `locale=zh-CN`、`timezone_id=Asia/Shanghai`，整轮复用同一上下文（不会每个商品新开进程）。
   先在浏览器中直接打开接口；数据不完整时再打开商品详情页建立正常会话，之后重新读接口。
3. **可见浏览器兜底** —— 每次新建**临时 Profile**（避免长期受限的旧环境反复失败），
   打开商品详情页后读取接口，当前商品处理完立即关窗清理临时 Profile。

请求间隔默认**随机 0.1 ~ 0.3 秒**（可在设置页改为 0.1 ~ 60 秒），使用随机区间而非固定值。

### 异常分类

| 类别 | 典型情形 | 处理方式 |
| --- | --- | --- |
| **临时失败** | HTTP 500/502/503/504、连接超时、连接重置、DNS 抖动、`Network.getResponseBody`、`Execution context was destroyed` | 先继续采集其他商品；整轮结束后等待 **5~15 秒**统一重试一次 |
| **风控受限** | HTTP 461 | 单轮累计达到阈值（默认 3 次）**立即熔断**，停止本轮请求，剩余商品入队，冷却 **15 分钟**后自动续采；绝不高频循环重试 |
| **明确下架** | 购买按钮 `unBuyableGoShop`、接口/页面出现「已下架，进店逛逛」「当前商品已下架」「商品不存在」「商品已失效」、`error_code=602 item not found`、「当前商品违规，无法展示」、item freeze | 转入下架列表：`active=0`，记录 `delisted_at` 与 `delisted_reason`，清除失败状态，保留历史快照，从后续任务中排除 |

重试成功的商品会自动从失败列表移除，并照常生成本地数据与企业微信时报。
一个商品失败**不会**卡死整轮任务（除非触发全局 461 熔断）。

> ⚠️ 判定下架的底线：**绝不**仅凭网络错误、空白页面或超时判定下架。

### 定时规则

- 默认周期 60 分钟，按**自然时间边界**调度。非整点启动不会把当前时刻当作正式整点。
- 每轮采集以该轮所属整点作为统计归属时间。
- 若 21:00 轮次尚未完成而时间已到 22:00，**立即打断 21:00 剩余任务并切换到 22:00 轮次**，
  不让旧任务无限积压。
- 全局线程锁保证「定时采集」与「立即采集」**不会重叠**。
- 所有网络与数据库重任务都在后台线程，界面通过主线程事件队列更新，GUI 始终响应。

### 采集字段

接口：`https://mall.xiaohongshu.com/api/store/jpd/edith/detail/h5/toc?version=0.0.5&item_id={商品ID}`

从 `data.template_data[0]` 解析：

| 字段 | 取值 |
| --- | --- |
| 商品标题 | `descriptionMain.name` → 回退 `descriptionH5.name` |
| 店铺名称 / ID | `sellerH5.name` / `sellerH5.id` |
| 商品主图 | `carouselH5.images[0].url`（`//` 开头补 `https:`） |
| 累计已售 | `priceH5.itemAnalysisDataText`（支持「已售123」「1.2万」「1.2w」） |
| 店铺累计销量 | `sellerH5.salesVolume` |
| 实际价格 | `priceH5.dealPrice.price` → `bottomBarMainH5.dealPrice.price` → `priceH5.highlightPrice` |
| 粉丝数 | `profitBarPopupH5.follow.fansNum` → `sellerH5.fansAmount` |
| 库存状态 | `carouselH5.stockStatus` |
| 是否可配送 | `bottomBarMainH5.deliveryInfo.ableToDelivery` |

**只有**接口明确 `success=true` 且 `template_data` 完整时，空的已售字段才解释为真实 0。
请求超时、状态码异常、返回体不完整、页面未加载、JSON 解析失败、元素缺失或安全校验，
一律判定本次采集失败，**绝不用 0 代替**。

**累计已售超过 10000 的商品不支持监控**：添加时直接提示并跳过；
存量商品一旦明确超过 10000，立即移出监控并停止继续请求。

## 七、销量统计口径

所有销量都由**累计已售快照的差值**计算，绝不把累计已售直接当作当日销量。
累计已售按**高水位**处理：取历史可信最大值，偶发读到更小的值不回退。

| 指标 | 口径 |
| --- | --- |
| 今日销量 | 当前可信累计已售 − 今日 00:00 累计高水位 |
| 昨日销量 | 今日 00:00 高水位 − 昨日 00:00 高水位 |
| 上小时销量 | 当前整点累计高水位 − 上一个完整整点小时的基线 |
| 某日销量 | 次日 00:00 高水位 − 当日 00:00 高水位 |
| 当日每小时销量 | 相邻整点累计高水位差值 |
| 模糊销售额 | 销量增量 × 当时实际价格（**模糊试算，不代表真实成交额**） |

关键约定：

- **0 点快照**既是前一天结束值，也是新一天基线，不会被重复计入两天。
- 软件当天**中途才开始监控**、没有 00:00 快照时，用当天第一条真实成功快照作为起始基线，
  并在界面上标记为不完整口径。
- 缺少足够基线时显示「**—**」，**不伪造 0**。
- 只有两个真实快照累计值确实相等时，增量才显示 0。
- 某个整点区间内没有任何真实快照时，该小时判定为「无数据」（显示「—」），
  不会把「采集失败」误显示成「0 销量」。
- 所有统计函数均处理跨日、0 点、缺少快照、重复快照与累计值偶发回退。

## 八、企业微信机器人通知

在「设置 → 企业微信机器人通知」中填入 Webhook、勾选启用、可发送测试通知，
并用「设置通知店铺」选择需要通知的店铺（支持全选、取消全选、搜索、保存）。
**只有勾选的店铺会发送**；一个都不勾选表示全部店铺。

Webhook 格式会在保存与发送前校验，发送失败只写入运行日志，**不影响采集数据保存**。
日志中的 Webhook 与 Cookie 均经过脱敏，不会明文落盘。

### 时报格式

```text
📊 12点店铺销量时报
08月17日 12:00 - 12:59

🥇 XXXXXXXX的店
上小时销量：22 单
今日总销量：24 单

🥈 XXXXXXXX的店
上小时销量：16 单
今日总销量：20 单

3. XXXXXXXX的店
上小时销量：9 单
今日总销量：9 单
```

前三名使用奖牌符号，其余使用序号；按上小时销量从高到低排序；
消息过长时按行边界自动拆分，不超过机器人单条限制。

若有失败商品，会再发送一条**采集失败通知**，包含时间、采集方式、失败数量、
商品名称、商品 ID 与原因。明确下架的商品不会作为临时失败反复通知。

## 九、只读 MCP 数据服务

`mcp_server.py`（或打包后的 `红薯雷达MCP.exe`）提供 stdio 通信的 MCP 服务，
只读打开同目录 `monitor.db`，**不提供任何增删改工具**。

### 可用工具

| 工具 | 说明 |
| --- | --- |
| `list_shops` | 店铺列表、监控商品数、今日销量、上小时销量、累计已售 |

## 十、数据维护与一键清理

顶部「一键清理」（始终可用，与其它功能开关无关）：

- 默认保留最近 **90 天**销量快照，并为**每个商品额外保留 1 条更早的基线**
  —— 缺了基线会导致近期销量无法计算，因此基线是硬性保留项；
- 日志默认保留 **30 天**；
- 执行 `WAL checkpoint` 与 `VACUUM` 回收空间；
- 清理前二次确认，完成后显示删除快照数、删除日志数、保留基线数与释放空间。

保留天数可在数据库中通过 `snapshot_keep_days` / `log_keep_days` 调整。

### 数据库表

- `products`：商品主表（`id, title, shop_name, shop_id, cover, active, created_at,
  last_error, delisted_at, delisted_reason`，另含失败状态与来源等扩展字段）
- `snapshots`：销量快照（复合主键 `product_id + captured_at`，含 `sold, shop_sold,
  price, fans, stock_status, deliverable`，并建立商品+时间、时间的索引）
- `settings`：键值设置
- `logs`：运行日志（自增 ID、时间、级别、来源、商品 ID、商品标题、摘要、完整详情）
- `deleted_products`：用户主动删除的商品，避免自动拓品时立刻回填

软件升级时会通过 `PRAGMA table_info` 检测并自动补齐新字段，
**不需要删除旧数据库**。所有 SQL 均为参数化查询，写入使用事务。

## 十二、隐私与安全

- 源码中**不写死任何个人 Cookie**；
- 浏览器 Profile、Cookie 文件与数据库只保存在本机程序目录；
- 日志写入前自动脱敏，**不落盘 Cookie、Webhook 完整值或其它敏感字符串**；
- 所有后台线程异常都会转换成界面可读提示，不会让 GUI 崩溃；
- 关闭软件时会尽量关闭 Playwright Context 与临时进程，并清理可见浏览器的临时 Profile；
- 数据库写入使用事务，避免中途退出留下半条记录；
- 图片下载、商品请求、通知推送均设置超时；
- 对长标题、空店铺、无封面、零销量、价格缺失、跨日等边界情况均有处理。
